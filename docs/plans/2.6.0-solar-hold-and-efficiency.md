# Battery Pilot 2.6.0: hold solar charging, and measured efficiency

## Context

2.5.0 (peak shaving, night charge only when it pays) is on `main`. From the list of further
optimisations the user picked two:

1. **Hold solar charging.** In self-use the battery takes the first morning surplus. On a dynamic
   contract it is then full at midday, when the sell price is negative and export is blocked, so the
   panels are throttled. The same happens on any contract when midday surplus exceeds the export
   limit. A "do not charge yet" action exports the morning surplus and keeps room for midday.
   The user does not know which Solis control exists or how the battery behaves in it, so: discover
   the feed-in priority switch, plan nothing without it, and assume the safe case.
2. **Measured efficiency.** The plan uses a fixed 90 % round trip, and the night-charge decision is
   close (28.7 c stored against 27.0 c saved). The user chose **show only**: the dashboard shows
   measured against configured; the plan keeps using the setting.

## A. New action `solar_hold`

Mirror of `peak_shave`, which already is "the battery does less than self-use" for deficit slots.

- **Discovery** (`discovery.ENTITIES`, `NEEDED_FOR`, `config.ENTITY_KEYS`, `config.yaml` `str?`,
  `translations/en.yaml`, DOCS.md): optional `feed_in_priority_switch`
  (switch, `feed_in_priority`). `App.can_solar_hold` like `can_peak_shave` (app.py:482).
- **`planner.optimize(..., solar_hold=False)`** (planner.py:228): in the per-level loop, where `held`
  is built for `x < 0` (shave), add the surplus case: when `solar_hold and x > 1e-9`, `y = 0`
  (no change), costed with `_flow(b, sl, 0, curtail_negative)`. `_cheapest` takes it as `held`
  unchanged; the choice is stored as a second marker `HOLD = "solar_hold"`. No action cost, no
  switch cost inside `PASSIVE` (add `solar_hold` to it). It is compared on the normal valuation
  only: holding leaves *less* in the battery, so the terminal value cannot favour it wrongly (the
  `low` gate stays for shave alone). Step building: `action = "solar_hold"`, `d = 0`.
  `make_plan`, `_boost`, `sticky_action`, `step_to_follow` pass it through as they do `peak_shave`.
  Not offered in a slot where `curtail_negative and sell < 0` (nothing can be exported).
- **`simulate.step()`**: `solar_hold` with `net < 0`: no charge, surplus exported (export limit and
  curtailment as now); with `net >= 0`: self-use.
- **`solis.Solis`**: `OPTIONAL += ("feed_in_priority_switch",)`; `solar_hold(t_local)`: time of use
  off, `_shave_off()`, switch on, `mode = "solar_hold"`; `_hold_off()` called by every other
  command, tracked like `shave` (`hold: bool | None`).
- **`controller.decide()`**: step `solar_hold` -> command `solar_hold` only while there is a real
  surplus (`pv_kw - load_kw > 0.2`); when the surplus is gone for 2 minutes -> `self_use` (safe case:
  the battery may sit idle in that mode). `Readings` already has `pv_kw`, `load_kw`; the 2-minute
  timer lives in `App` (one timestamp), so `decide` stays pure with a `surplus_gone_s` argument.
  `solar_hold` joins `controller.ACTIVE` (control off, blind, restart, shutdown return to self-use).
- **`app.py`**: `_apply` maps the command; `_reconcile` reads the switch back as it does the
  peak-shaving one; pass `solar_hold=` to `make_plan` and `compare.replay_day`.
- **Dashboard** (`static/index.html`): `ACTIONS`, colour `--hold`, legends, plan note.
- **`tests/fake_ha.py`**: ctor option `feed_in_priority=False`; in that mode surplus is exported and
  a deficit is fed from the grid (the safe assumption). `tools/yearsim.py --solar-hold`.

## B. Measured efficiency (show only)

No new entity: from the stored `QuarterRecord`s (meter.py:25), battery AC flow of a quarter =
`load + export − import − pv`, and its SOC change = next record's `soc` − this one's.

- New `pilot/efficiency.py`: `EfficiencyMeter` with three running sums of (AC kWh, SOC points):
  grid charge (`pv` ≈ 0, flow in), solar charge (flow in, `pv` > 0), discharge (flow out).
  Only quarters with full coverage on all four channels, an SOC at both ends, and inside 15-95 %
  SOC (the Solis SOC is unreliable at the ends). `learn_records(recs)` is called from `nightly()`
  next to `shade.learn_records` (app.py:706); sums decay with a 60-day half-life; saved in
  `state.json`.
- Result: AC kWh per SOC point in and out; round trip = out / in (battery capacity cancels), given
  only once each side has 150 SOC points, else "not enough data yet (n of 150)".
- Published as `sensor.battery_pilot_efficiency` (state: measured round trip %, attributes: grid
  and solar charge separately, points measured, configured value) and a dashboard line
  "Round trip: measured 86 % (setting 90 %)", with a hint when they differ by 3 points or more.
  DOCS.md: sensor and how to act on it. The plan itself is unchanged.

## Verification

- Planner tests: dynamic day with negative midday sell and export blocked -> `solar_hold` in the
  morning, less curtailed, lower cost than without; day with surplus above the export limit on a
  fixed contract -> hold before the peak; flat sell and no clipping -> never planned; no switch
  entity -> never planned; 2.5.0 plans unchanged when the flag is off.
- simulate/controller/solis tests: energy balance; command order; switch off before every other
  command; return to self-use after 2 minutes without surplus; control off, blind, restart, shutdown.
- e2e with `fake_ha`: a summer day with negative prices curtails less with the switch.
- Efficiency: synthetic records with a known 85 % round trip are measured within 1 point; too
  little data gives no value; bad quarters (gaps, SOC ends) are skipped; sensor in DOCS
  (`test_packaging`).
- `pytest -q`, `ruff check .`, `python tools/yearsim.py` with and without `--solar-hold` on both
  contracts: totals must not get worse; report curtailed kWh and cost.
- Not verifiable here: the real inverter's feed-in priority behaviour. First sunny day: watch that
  the switch turns on in the morning, export shows, and the battery charges again at midday.
